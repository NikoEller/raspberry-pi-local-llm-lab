01 / THE RESULT

The faster clock wins.
Just not everywhere.

Moving from 2.6 to 2.8 GHz clearly accelerated prompt ingestion, but token generation barely moved. That is the signature of a workload becoming constrained by memory bandwidth rather than raw CPU frequency.

The recommendation is straightforward: 2.8 GHz is the confirmed daily profile at roughly 55 °C with throttled=0x0. A first 3.0 GHz llama-bench run has now reached 11.50 pp128 and 2.45 tg128 tokens/s, but it still needs a longer stability and temperature record.

NEW · LLAMA-BENCH AT 3.0 GHz

A promising peak.
With visible run-to-run variation.

Two four-thread runs used the same 4.68 GiB Qwen3-8B Q4_K_M model. Prompt processing stayed tightly grouped, while generation moved from 2.45 to 2.30 tokens/s. More repetitions are needed before declaring a stable median.

The GGUF file is not the entire memory budget. Linux, runtime buffers, and the KV cache all need space. A 4,096-token context is a sensible balance on this machine; 8,192 may fit, but reduces safety margin.

03 / OVERCLOCK

Three gigahertz,
one careful step at a time.

The stable 2.8 GHz result is the control. Change one variable at a time, keep a recovery copy, and only accept 3.0 GHz after sustained error-free testing.

!
Overclocking is silicon-specific.

It can cause crashes, silent calculation errors, storage corruption, higher power draw, and shorter component life. A configuration stable on one Pi may fail on another.

01

Back up the boot configuration

Raspberry Pi OS reads these settings before Linux starts. Make recovery possible before changing anything.

TERMINAL
sudo cp /boot/firmware/config.txt \
  /boot/firmware/config.txt.bak-2800
02

Change the existing overclock block

Edit existing values rather than appending duplicates. For llama.cpp, test the CPU first; the GPU clock does not accelerate CPU inference.

/BOOT/FIRMWARE/CONFIG.TXT
[all]
over_voltage_delta=50000
arm_freq=3000
Why no gpu_freq? The model runs on the Arm cores. Adding gpu_freq=1000 creates another stability variable without a meaningful llama.cpp speed benefit. Test it separately only for a GPU workload.
03

Reboot, verify, then load the system

Do not use force_turbo=1. Let dynamic frequency scaling reduce clock and voltage when the board is idle.

TERMINAL
sudo reboot

# after reconnecting
vcgencmd get_config arm_freq
vcgencmd get_config over_voltage_delta
vcgencmd get_throttled
RECOVERY PLAN

If the Pi does not boot

Power down, attach the boot media to another computer, open the boot partition, and restore config.txt.bak-2800 as config.txt. Never test a risky clock without this escape route.

05 / TEST PROTOCOL

A fast result is nice.
A repeatable result is useful.

01

Hold inputs constant

Use the identical prompt, context size, sampling parameters, thread count, model file, and maximum output length.

02

Warm the model

Discard the first run after startup. It includes cold filesystem pages and is not comparable with later runs.

03

Repeat five times

Record prompt tok/s and generation tok/s separately. Use the median to reduce noise from background activity.

04

Watch the machine

Track actual clock, temperature, throttling, available RAM, and swap while the response is generated.

05

Test for errors

A completed response is not a stability test. Run sustained CPU verification and check kernel logs for hardware symptoms.

06

Change one variable

CPU, voltage, GPU, context, and model quantization should never all change between benchmark runs.

LIVE TELEMETRY

Keep this visible during every run.

  • Clock: close to the configured maximum under full load
  • Temperature: comfortably below the 85 °C thermal limit
  • Throttle: 0x0 before and after testing
  • Memory: at least ~1 GB available, with no sustained swap growth

TROUBLESHOOTING

Signals worth respecting.

The Pi reboots or freezes under load+

Return to 2.8 GHz first. If 3.0 GHz is essential, verify power delivery and cooling before changing voltage. Do not keep raising voltage to rescue a poor silicon sample.

get_throttled is not 0x0+

The bitmask records current and historical undervoltage or thermal events. Reboot only after fixing the cause, then retest from a clean state.

The model gets slower during long chats+

Longer prompts require more prompt evaluation, and a growing KV cache consumes memory. Check context size, available RAM, swap, and whether old conversation history is being resent.

Higher quantization does not increase tok/s+

That is expected. Q5 or Q8 usually improves fidelity while increasing model size and memory traffic. Q4_K_M is the balanced choice here; smaller quants or fewer parameters usually improve speed.

The server will not start after editing+

Run systemctl status qwen.service and inspect the journal. Confirm the binary and GGUF paths and ensure the edited ExecStart remains one valid line.
